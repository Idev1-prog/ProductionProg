# Архитектура Risk Orchestrator

## 1. Контекст

В банке работают два независимых потока расчётов:

- **регламентный (auto)** — ночной цикл с жёстким SLA;
- **ручной (manual)** — аналитики и методологи пересчитывают произвольные даты.

Потоки не знают друг о друге, поэтому возникают гонки записи, дедлоки и
«тихая» порча данных. Оркестратор — дирижёр: он не считает риски и не хранит
бизнес-данные, а управляет метаданными, очерёдностью и блокировками.

## 2. As-Is / To-Be

| As-Is | To-Be |
|---|---|
| Запуски неупорядочены | Единая очередь с детерминированным приоритетом |
| Нет изоляции по данным | Гранулярные блокировки `resource_key`, RAW/WAW-анализ |
| Нет визуализации | Гант, heatmap, журнал конфликтов, очередь |
| Веса приоритетов зашиты в код | Конфигуратор `/settings`, применяется на лету |
| Ручной поток страдает от ночного цикла | Абсолютный приоритет + вытеснение auto |
| Состояние в памяти процесса | In-memory + опциональный SQLite-снимок |

- `frontend/` общается исключительно по HTTP, не зная внутренностей.

## 4. Модель данных

- `Process` — id, имя, поток, ресурсы, срочность, длительность, SLA, статус,
  приоритет, временные метки, прогресс, причина блокировки, метаданные.
- `Resource` — `key` (таблица/срез/дата), `mode` (read/write), `service`.
- `Lock` — кто (`process_id`), что (`resource_key`), как (`mode`), когда взял.
- `PrioritySettings` — веса и лимиты, меняются через API/UI.

`resource_key` — главный инструмент гранулярности. Примеры:

```text
dm_credit.portfolio
dm_credit.portfolio:2026-11-25
dm_market.quotes:equity
```

## 5. Алгоритм планировщика

Фоновый цикл в `main.py` каждые `tick_interval` секунд вызывает `tick()`:

1. **Завершение.** Для всех `running` проверяется `started_at + duration`.
   Истёкшие переводятся в `completed`, блокировки снимаются.
2. **Пересчёт приоритетов** для `queued/blocked/running` — SLA «плывёт»,
   starvation растёт.
3. **Сортировка** кандидатов (`queued` + `blocked`) по убыванию приоритета,
   затем по `created_at` (FIFO при равенстве).
4. **Запуск.** Пока есть свободные слоты (`max_running`):
   - проверить конфликты с активными блокировками;
   - если конфликтов нет — взять блокировки и перевести в `running`;
   - иначе — `blocked`, записать конфликт в журнал (дедупликация по подписи).
5. **Preemption.** При добавлении manual-процесса, конфликтующего с running
   auto-процессом, auto немедленно останавливается, его блокировки снимаются,
   статус → `blocked`, причина → «вытеснен ручным», в журнал пишется `OVERRIDE`.

### Формулы приоритета

```text
manual = max(1000, manual_base) + urgency·5 + min(wait, 300)·0.1
auto   = sla_weight·(SLA/100) + urgency_weight·(urgency/10)
       + starvation_weight·(wait/100)

SLA        = 100, если дедлайн прошёл; 0, если до него ≥ 10 минут
starvation = min(100, wait / 5 минут · 100)
```

Диапазон auto — примерно 0..100, manual — от 1000. Поэтому ручной поток
не может проиграть автоматическому даже при экстремальных весах.

## 6. Конфликты и блокировки

| Активная блокировка | Запрос | Результат |
|---|---|---|
| read | read | совместимо |
| read | write | RAW |
| write | read | RAW |
| write | write | WAW |

- Блокировка берётся на весь набор ресурсов процесса атомарно: либо все, либо
  ни одной (частичного захвата нет).
- Блокировки снимаются при `completed`, `cancelled`, `pause` и `preempt`.
- Конфликт логируется один раз на пару «процесс + набор блокирующих», чтобы
  тик не засорял журнал.
- `blocked_by` хранит id процессов-блокираторов, `blocked_reason` — человекочитаемую
  причину.

## 7. Машина состояний

```text
queued ──► running ──► completed
  │           │
  │           ├──► paused ──► queued (resume)
  │           ├──► blocked ──► running (ресурс освободился)
  │           └──► cancelled
  ├──► blocked ──► running
  ├──► paused ──► queued
  └──► cancelled

completed / cancelled / failed ──(restart)──► queued
```

Переходы валидируются в `state_machine.py`; недопустимый переход — `400`.
`restart` — единственное явное исключение: он сбрасывает терминальный статус.

## 8. API и контракты

- `backend/schemas.py` — единственный источник правды для DTO.
- Контракт описан в `docs/api_contract.md`, заморожен после 0:30.
- Ошибки: `400` бизнес-логика, `404` отсутствие процесса, `422` валидация.
- UI не парсит внутренние структуры, только поля контракта.

## 9. Персистентность и отказоустойчивость

MVP:

- по умолчанию состояние в памяти;
- при `RISK_PERSIST=1` каждый мутирующий вызов сохраняет JSON-снимок в SQLite
  (`data/orchestrator.db`, таблица `snapshot`);
- при старте снимок восстанавливается, `running`-процессы возвращаются в
  `queued` (блокировки не восстанавливаются — их берут заново).

Это демонстрирует требование «очередь не теряется при падении ноды», но не
заменяет production-хранилище (PostgreSQL/Redis) и распределённые локи.

## 10. Производительность

- Тик — O(n log n) на сортировку, n — число активных процессов.
- Для demo-нагрузки (сотни процессов) этого достаточно.
- Latency постановки: `add_process()` делает один тик синхронно, укладывается
  в десятки миллисекунд.
- Узкое место при росте: глобальная сортировка и in-memory локи. Дальше —
  шардирование по `resource_key` и вынесение очереди в Redis.

## 11. Ограничения MVP и развитие

| Ограничение | Что дальше |
|---|---|
| Симуляция вместо реальных расчётов | адаптеры к очередям/воркерам (Celery, Kafka) |
| Один процесс оркестратора | leader election + распределённые локи |
| Пауза перезапускает с нуля | чекпоинты прогресса |
| Нет авторизации | RBAC (аналитик/система/админ), JWT |
| SQLite-снимок | PostgreSQL + outbox, идемпотентные операции |
| Нет webhooks | callback/webhook при смене статуса |
| Нет графа зависимостей | DAG процессов и data lineage |

## 12. Почему так

- **Ядро без фреймворков** — быстрые юнит-тесты и переносимость.
- **Тик вместо нативных asyncio-задач** — детерминированное демо, легко
  воспроизвести конфликт и показать очередь в любой момент.
- **Гранулярные ключи вместо блокировки БД** — параллелизм там, где данные
  не пересекаются.
- **Ручной поток через `manual_base ≥ 1000`** — абсолютный приоритет
  гарантирован математически, а не «настройкой по умолчанию».
