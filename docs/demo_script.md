# Сценарий выступления перед жюри (7 минут)

## Подготовка за 2 минуты до выхода

1. Запустить API:

   ```powershell
   uvicorn backend.main:app --port 8000
   ```

2. Запустить UI:

   ```powershell
   streamlit run frontend/app.py
   ```

3. Открыть два окна: UI (`http://localhost:8501`) и Swagger
   (`http://127.0.0.1:8000/docs`).
4. Нажать «Сбросить состояние» в сайдбаре.
5. Проверить, что автообновление включено (2 сек).

## 0:00–0:40. Проблема

> «В банке два потока расчётов: ночной регламент и ручные пересчёты. Они не
> знают друг о друге. Утром обнаруживается, что отчёт построен по грязным
> данным, а аналитик два часа ждал, пока ночной цикл отпустит таблицу.
> Наша задача — поставить между ними диспетчера».

Показать `Требования.md` / слайд «As-Is».

## 0:40–1:30. Что сделали

> «Risk Orchestrator принимает метаданные процесса, строит очередь по
> приоритету, проверяет конфликты RAW/WAW по конкретным ресурсам, показывает
> Гант и даёт настраивать веса без перезапуска».

Показать вкладки UI: Дашборд, Гант, Очередь, Управление, Настройки.

## 1:30–2:30. Демо 1 — happy path

Действия:

1. Вкладка «Управление» → сценарий `scenarios/01_happy_path.json` →
   «Загрузить».
2. Перейти на «Дашборд» и «Гант».

Реплика:

> «Четыре процесса на разных ресурсах. Все стартуют параллельно, конфликтов
> нет, утилизация близка к 100%. Гант показывает реальные окна выполнения».

Ожидаемо: `conflicts_total = 0`, процессы в `running/completed`.

## 2:30–3:30. Демо 2 — WAW и RAW

Действия:

1. Загрузить `02_waw_conflict.json` с галочкой «Сбросить».
2. Открыть «Очередь и конфликты».

Реплика:

> «Два процесса пишут в `dm_credit.portfolio`. Второй не запускается: WAW.
> Он не падает и не ретраит — он встаёт в очередь с причиной. В журнале видно,
> кто кого блокирует. Как только первый завершится, второй стартует сам».

3. Загрузить `03_raw_conflict.json`.

> «Теперь читатель против писателя — RAW. Отчёт не читает недокоммиченные
> данные, а ждёт освобождения ресурса. Это и есть защита от тихой порчи».

## 3:30–4:30. Демо 3 — ручной override

Действия:

1. Загрузить `04_manual_override.json` с «Сбросить».
2. Открыть «Очередь и конфликты».

Реплика:

> «Ночной пересчёт пишет портфель. Приходит аналитик с ручным пересчётом того
> же ресурса. Ручной поток имеет абсолютный приоритет: ночной процесс
> вытесняется, его блокировки снимаются, аналитик стартует сразу. В журнале —
> `OVERRIDE`. После завершения ручного ночной вернётся в очередь».

Показать `priority`: manual ≈ 1045, auto ≈ 70–90.

## 4:30–5:20. Конфигуратор

Действия:

1. Вкладка «Настройки».
2. Двинуть «Вес SLA» до 80, «Вес срочности» до 15, «Вес защиты от голода» до 5.
3. Сохранить.
4. Вернуться в «Очередь»: порядок пересчитался.

Реплика:

> «Политика приоритетов — не код, а конфигурация. Планировщик пересчитывает
> очередь на следующем тике. Ручной поток всё равно выше: `manual_base`
> ограничен снизу 1000».

## 5:20–6:10. Архитектура и надёжность

Показать `docs/architecture.md` (схема) и Swagger.

Реплика:

> «Ядро не знает про FastAPI — оно тестируется отдельно. API-контракт
> заморожен, frontend ходит только по нему. Есть SQLite-снимок: при падении
> очередь восстанавливается, running возвращается в queued. 17 тестов
> (приоритеты, конфликты, smoke API) запускаются одной командой `pytest -q`».

## 6:10–6:50. Ценность и развитие

> «Что получает банк: предсказуемый ночной цикл, ручные задачи не ждут часами,
> данные не портятся молча, инцидент разбирается по журналу за минуты.
> Дальше — распределённые локи, PostgreSQL, RBAC, прогноз длительности и

## Резервные сценарии

### Если API не поднялся

```powershell
uvicorn backend.main:app --port 8000
```

Проверить `http://127.0.0.1:8000/health`. В UI нажать «Сбросить состояние».

### Если UI завис на автообновлении

Выключить «Автообновление» в сайдбаре, обновить страницу `F5`.

### Если демо-сценарий не загрузился

```powershell
python scripts/seed.py --reset --scenario data/scenario.json
```

### Если не хватает времени

Пропустить happy path, сразу показать WAW → OVERRIDE → настройки. Это ядро
ценности.

## Вопросы жюри и короткие ответы

**Почему не используете существующий планировщик (Airflow/Celery)?**
> Для банковского кейса важна не только очередь, но и семантика данных:
> RAW/WAW по гранулярным ключам и абсолютный приоритет ручного потока. Мы
> сделали слой, который может работать поверх Celery/Airflow; в MVP ядро
> автономно и тестируемо.

**Что будет при двух экземплярах оркестратора?**
> Сейчас — один экземпляр. В development: leader election + Redis-локи,
> идемпотентные ключи запусков. Ограничение зафиксировано в architecture.md.

**Как считается приоритет?**
> Формула на слайде и в `settings_panel.py`: SLA + срочность + starvation.
> Ручной — `manual_base` ≥ 1000, поэтому всегда первый.

**Что если процесс завис?**
> В MVP длительность симулируется, поэтому зависаний нет. В production —
> heartbeat воркера, таймаут, `failed`, автоматический retry с идемпотентностью.

**Где хранятся данные?**
> Оркестратор не хранит бизнес-данные, только метаданные и состояния. Это
> требование loose coupling. Снимок состояния — SQLite/PostgreSQL.
